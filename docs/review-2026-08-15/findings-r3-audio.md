# Round 3, F4 — the engineer's audio path

## Straight answer
**On this machine today: the proactive engineer probably works, push-to-talk definitely does
not, and neither can tell him which.**

- Engine chain resolves to `VoicePackEngine(en_GB-alan-medium, 417 clips, fallback=PiperEngine)`
  in 0.64 s; Piper synthesises a race call to first audio in 0.06-0.15 s. There IS a working
  voice on the machine and the pack is real.
- **PTT is dead right now.** PortAudio's default input is index 1, "Microphone (JBL Endurance
  Run 3" — a Bluetooth headset that is NOT CONNECTED. `InputStream` opens without error and
  delivers **zero audio callbacks**; six consecutive 3-second holds captured 0.00 s each.
  The Intel array (device 2) delivers 19 blocks in the same 2 s, so it is the device, not the
  code. SAPI times out after 5 s and Moonshine takes over, so this IS the live race path.

## Findings
- **R1 · P1 · voice.py:330 — `VoicePackEngine.speak()` has NO `else` on the fallback branch.**
  When `_fallback` is None it returns having produced no sound and raised nothing, so
  `Voice._run`'s except never fires. `_best_engine` builds exactly that object: if both
  `PiperEngine()` and `Sapi5Engine()` raise, `load_voice_pack(live)` still returns
  `VoicePackEngine(folder, clips, fallback=None)` when a rendered pack is on disk. `Voice.enabled`
  (voice.py:63) is `self._engine is not None` — **it tests that an object exists, not that a
  sound can be made.** Constructed that state directly: `enabled: True, engine_name: voice-pack,
  zero audio, INFO/WARNING only`. Models and pack are independently .gitignored so this state
  is reachable.
- **R2 · P1 · controller.py:819 — `test_voice` reports "Said it through <engine>" BEFORE any
  synthesis is attempted.** `say()` is asynchronous (appends to `spoken`, puts on a Queue,
  returns); the success message is keyed on `enabled`. **The one control that exists to prove
  the voice works can never fail.** Every failure below the queue — dead device,
  PortAudioError, fallback-less pack, hung SAPI — produces the identical line.
- **R3 · P1 · voice.py:255 (and :343) — the output device is whatever PortAudio picked at
  import, and a device that is not there ACCEPTS THE AUDIO WITH NO ERROR.**
  No `device=` on any stream; no audio-device field in `Settings`; nothing ever calls
  `sd._terminate()/_initialize()`. Measured: wrote 1.00 s of tone to the disconnected JBL —
  **completed in 2.53 s with NO ERROR.**
  *What he hears putting the PSVR2 on mid-race:* if the old device still exists, the engineer
  speaks into it, `hits` increments, the call is written to the race screen and
  `append_revision`, and the man in the headset hears nothing with every indicator green.
  If it has gone, `PortAudioError` is swallowed three times over (pack → Piper → `_run`),
  logged at ERROR, and the silence is **permanent for the session** — nothing re-enumerates.
- **R4 · P1 · ptt.py:383 — a capture device yielding ZERO frames is reported as "no speech in
  the capture", indistinguishable from the driver not talking.** `duration_s == 0.0` is never
  distinguished from a short capture. Combined with E9 (all five reasons speak "Say again."),
  the driver gets no signal at all that his microphone is not there. Measured: 6/6 cycles
  captured 0 blocks, `last_reason='no speech in the capture'` every time.
- **R5 · P2 · voice.py:325 — a playback failure FALLS THROUGH into the miss counter and the
  miss log.** The catch at :319 logs "synthesising instead" and does not return, so control
  reaches the miss path and logs "voice pack miss: <text> - not in the manifest" — for a line
  that WAS in the manifest. The class docstring says "the miss log is how the manifest gets
  finished", so the artefact used to decide what to render is polluted by device errors.
  Reproduced exactly with `'Say again.'`, a line in the 417-clip manifest.
- **R6 · P2 · phrase_manifest.py:51 — the 417-clip pack covers NONE of the proactive race
  calls.** Every clip is generated by walking `intents.answer()` — the PTT replies only.
  Nothing is generated from `race/calls.py::Call.spoken()`. Measured **0/7 coverage** over six
  real `RaceState`s: "10 to go.", "Chequered flag.", "Map 3 down the straights…",
  "You can push…", "Box next lap. Stop 1, on the plan.", "Green, green, green. 20 laps." —
  all MISS. **So the proactive channel has no pack path and therefore no second engine behind
  it: every unprompted call rides on Piper alone.**
  Also `_looks_like_plan_summary` is `"," in text and text not in fixed_lines()` — not a test
  for a plan summary at all, so it attaches a confident wrong explanation ("the plan summary is
  combinatorial…") to lines like the green-flag call.
- **R7 · P3 · shift_beep.py:117 — `test_beep` reports success even when the beep raised.**
  Same unconditional-success pattern as R2. `_play` swallows and `play_now` returns True
  regardless.

## REJECTED — N8, the hook-timeout hypothesis. Drop it.
Steady-state `begin()` = 35-38 ms, `end()` = 33-44 ms; the 1.6 s/5.1 s first cycle was cold
device-open and first-inference cost, not per-press. `LowLevelHooksTimeout` is not set in
`HKCU\Control Panel\Desktop`. Blocked pynput's `on_press` for 2.0 s and then 6.0 s while
injecting keypresses: **6/6 and 5/5 still delivered, listener still running.** The hook
survives a six-second block. Caveat: injected events, not a physical wheel button — but
6 s tolerated against 40 ms used is a large margin.

## PHYSICAL UAT CHECKS — cannot be done from code
1. Connect the JBL (or change the Windows default input) and press PTT. If it still answers
   "Say again." to a clear "how much fuel", recognition is broken independently of the device.
2. **The decisive test:** start the app with the headset OFF, then put the PSVR2 on and press
   "Test engineer voice", listening in the PSVR2. Prediction: it says "Said it through
   voice-pack" and you hear nothing.
3. Reverse: start WITH the PSVR2 on, disconnect it mid-session, press Test voice again.
   Prediction: still reports success; check `logs/` for `PortAudioError`.
4. Start a race with the correct headset on from launch, run five laps. The green-flag call and
   the five-lap status are the audible proof the proactive channel is alive.
5. Press "Test beep" with the headset on and off and compare with the voice test.
   `winsound.Beep` re-resolves the Windows default each call while `sounddevice` does not —
   **if you hear the beep in the PSVR2 but not the voice, that confirms the stale-device
   diagnosis outright.**
